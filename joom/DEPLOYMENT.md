одноразовый Secret; после замен сервера множества прав совпадают с исходными.
S3 versioning включён. ACL отдельных серверов не синхронизируются непрерывно.
Одновременное редактирование одной note в разных серверах может перезаписать
изменения; откат сервера не отменяет уже сохранённые изменения общего файла.

Прошли 11 целевых server tests. Для больших коллекций UI использует штатный
virtual viewport вместо отрисовки всего корня (в архиве 1 669 корневых элементов).
Production UI build успешен. Самостоятельный search index пересобирается в фоне;
перечень папок не зависит от его готовности. Notebook cron выключен.

Текущий server image: `0.12.1-joom-1-shared`, source
`00372424fa04aea639d9832d1c16d11f908c0864`, digest
`sha256:dab60e463b567291adfb73c1b8d7c79c4d97b81277488601c4bbe4a1f037db03`.
Interpreter и Spark образы прежние. Подробные диагностические файлы сохранены

## Ошибки, обнаруженные во время переноса

Дополнительно к восстановленным Joom-патчам исправлены и проверены:

1. Общий унаследованный registry websocket handlers приводил к вызову обработчика
   published-paragraph на обычном редакторе и потере текста.
2. REST-редактирование обходило NotebookService и не отправляло событие индексации.
   Теперь HTTP и websocket пути обновляют индекс.
3. После клонирования Angular переиспользовал компонент: URL менялся, а исходная
   note оставалась в редакторе. Загрузка теперь зависит и от route params, поздний
   NOTE другой note отвергается. Исправлен timer фокуса удалённого rename input.
4. Позднее закрытие старой interpreter group удаляло новую group с таким же ID,
   оставляя pod без управления. Реальный fault-cycle выявил orphan; детерминированный
   тест до исправления получал null вместо replacement. Удаление теперь проверяет
   строгую идентичность экземпляра под write lock. Сравнение через equals не подходит:
   InterpreterGroup сравнивает только ID. После исправления прошли полные 20 циклов.
5. При UID1000 официальный образ не позволял создать Jetty work directory.
   Права изменены только на необходимые runtime directories.

Исходные неуспешные прогоны сохранены как доказательства, не засчитаны как успешная
серия. Контролируемые ERROR при cancel, ошибочном SQL и потере запуска являются
ожидаемыми результатами отрицательных сценариев.

## Что исключено и что остаётся неопределённым

- HBase больше не используется: его `HADOOP_USER_NAME` workaround исключён.
  Spark всё ещё использует Hadoop filesystem APIs; это не утверждение об отсутствии
  любых Hadoop-библиотек. Реальные GCS/proxy-user операции прошли без этой переменной.
- Trino исключён по прямому уточнению пользователя. Его устаревший endpoint удалён
  только из нового стенда. Старый внешний JDBC 1.4.0 JAR не накладывался на 0.12.1.
- Механизмы comparator/null-form уже есть upstream. Старые классические AngularJS
  реализации заменены работой с новым Angular UI; classic UI не является целью пилота.
- Две фактические ротации токена проверялись на исходном upstream-аудите с Fabric8
  6.13.4. Это отдельное доказательство; итоговым образам не приписывается новый
  многократный token-rotation soak. DNS retry покрыт детерминированной инъекцией,
  обычный успешный запуск pod не доказывает отсутствия DNS-race.
- Сохранение обоих локальных текстов в двух вкладках не является автоматическим
  merge конфликтующих сохранений; такой merge не добавлялся.
- Живая корпоративная SSO-сессия браузера через весь proxy/login redirect ещё
  требует проверки человеком. Проверены адаптированный remote-user backend и
  сохранение черновика при реальном Shiro login с инъекцией 401.
- Все ~43 тысячи исходных ноутбуков, производственная нагрузка, Comet и остальные
  коннекторы не проходили полный business end-to-end. Следующий этап — выбранные
  рабочие сценарии и проверка capacity/массовой миграции перед production.

**Конечные серии проверок не доказывают отсутствие мигающих ошибок.** В отчёте
разделены обнаруженные дефекты, эквивалентные upstream-механизмы, исключённые
компоненты и оставшиеся ограничения. Исходные аргументы за непроверенные патчи
сохранены в PORTS.md и первоначальном audit report.

## Воспроизведение и откат

В deployment-ветке есть `README-012.md`, `install-test-012.sh` и отдельный
`chart-012` со всеми Helm values в его `values.yaml`. Локальные raw logs, browser
traces/state, credentials, оригинальные note JSON и cluster backups остаются в
закрытом `/private/tmp/zeppelin-012-balloon`; в Git их нет.

Для немедленного возврата URL на старый balloon:

```sh
kubectl --context analytics-gke -n zeppelin-test delete ingress zeppelin-server-012
kubectl --context analytics-gke -n zeppelin-test scale deployment zeppelin-server-012 --replicas=0
```

Старый релиз и его данные остаются на месте. Повторный `install-test-012.sh`
возвращает pilot. PVC пилота помечены `helm.sh/resource-policy: keep`; их удаление
требует отдельного решения после окончания проверки.
